# TDD 测试驱动开发

> 测试驱动开发框架，强调行为测试、垂直切片方法。

---

## 核心理念

**测试应通过公共接口验证行为，而非实现细节。** 代码可以完全改变，测试不应该改变。

**好的测试**是集成风格的：通过公共 API 验证真实代码路径。它们描述系统做什么，而不是怎么做。好的测试读起来像规格说明。

**坏的测试**耦合于实现细节。它们 mock 内部协作者、测试私有方法。警告信号：重构时测试失败但行为未变。

---

## 反模式：水平切片

**不要先写所有测试，再写所有实现。** 这是"水平切片"。

```
错误（水平）：
  RED:   test1, test2, test3, test4, test5
  GREEN: impl1, impl2, impl3, impl4, impl5

正确（垂直）：
  RED→GREEN: test1→impl1
  RED→GREEN: test2→impl2
  RED→GREEN: test3→impl3
```

## 工作流

### 1. 规划

- [ ] 确认需要哪些接口变更
- [ ] 确认要测试哪些行为（优先级排序）
- [ ] 识别深度模块的机会（小接口，深实现）
- [ ] 为可测试性设计接口
- [ ] 列出要测试的行为（不是实现步骤）
- [ ] 获取用户批准

### 2. 曳光弹

先写一个测试确认一件事：
```
RED:   写第一个行为的测试 → 测试失败
GREEN: 写最少代码通过 → 测试通过
```

### 3. 增量循环

对每个剩余行为：
```
RED:   写下一个测试 → 失败
GREEN: 最少代码通过 → 通过
```

规则：
- 一次一个测试
- 只够通过当前测试的代码
- 不要预判未来测试
- 保持测试聚焦于可观察行为

### 4. 重构

所有测试通过后，寻找重构机会：
- [ ] 提取重复
- [ ] 深化模块（将复杂度移到简单接口后面）
- [ ] 应用 SOLID 原则
- [ ] 考虑新代码揭示的现有代码问题
- [ ] 每次重构后运行测试

**绝不在 RED 时重构。** 先到 GREEN。

## 深度模块

**深度模块** = 小接口 + 大实现

```
┌─────────────────────┐
│   小接口             │  ← 少量方法，简单参数
├─────────────────────┤
│                     │
│   深实现             │  ← 复杂逻辑隐藏
│                     │
└─────────────────────┘
```

**浅模块** = 大接口 + 薄实现（避免）

设计接口时问自己：
- 能减少方法数量吗？
- 能简化参数吗？
- 能隐藏更多复杂度吗？

## 可测试性接口设计

1. **接受依赖，不要创建依赖**

```typescript
// 可测试
function processOrder(order, paymentGateway) {}

// 难测试
function processOrder(order) {
  const gateway = new StripeGateway();
}
```

2. **返回结果，不产生副作用**

```typescript
// 可测试
function calculateDiscount(cart): Discount {}

// 难测试
function applyDiscount(cart): void {
  cart.total -= discount;
}
```

3. **小接口面积** — 更少的方法 = 更少的测试

## Mock 使用指南

**仅在系统边界 Mock：**
- 外部 API（支付、邮件等）
- 数据库（有时 — 优先使用测试数据库）
- 时间/随机性
- 文件系统（有时）

**不要 Mock：**
- 自己的类/模块
- 内部协作者
- 任何你控制的东西

**使用依赖注入**传递外部依赖，而非内部创建。

**优先使用 SDK 风格的接口**，每个函数独立可 mock：
```typescript
// GOOD: 每个函数独立可 mock
const api = {
  getUser: (id) => fetch(`/users/${id}`),
  getOrders: (userId) => fetch(`/users/${userId}/orders`),
};

// BAD: mock 需要条件逻辑
const api = {
  fetch: (endpoint, options) => fetch(endpoint, options),
};
```

## 好测试 vs 坏测试

### 好测试特征

```typescript
test("用户可以用有效购物车结账", async () => {
  const cart = createCart();
  cart.add(product);
  const result = await checkout(cart, paymentMethod);
  expect(result.status).toBe("confirmed");
});
```

- 测试用户/调用者关心的行为
- 仅使用公共 API
- 在内部重构后存活
- 描述 WHAT，不是 HOW
- 每个测试一个逻辑断言

### 坏测试红旗

- Mock 内部协作者
- 测试私有方法
- 断言调用次数/顺序
- 重构时测试失败但行为未改变
- 测试名称描述 HOW 而非 WHAT
- 绕过接口验证

---

## 重构候选项

TDD 周期后寻找：
- **重复** → 提取函数/类
- **长方法** → 拆分私有辅助方法（测试保留在公共接口）
- **浅模块** → 合并或深化
- **特性依恋** → 将逻辑移到数据所在位置
- **基本类型偏执** → 引入值对象
- **新代码揭示的现有代码问题**

---

## 每周期检查清单

```
[ ] 测试描述行为，不是实现
[ ] 测试仅使用公共接口
[ ] 测试能在内部重构后存活
[ ] 代码为此测试最小化
[ ] 没有添加推测性功能
```
