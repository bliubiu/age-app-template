# 对话转 PRD

> 将当前对话上下文转化为 PRD 并发布到项目 Issue 跟踪器。

---

## 流程

### 1. 探索代码库

了解代码库的当前状态。在整个 PRD 中使用项目的领域词汇表，尊重相关的 ADR。

### 2. 勾勒模块

勾画出需要构建或修改的主要模块。积极寻找机会提取可以独立测试的深度模块。

深度模块（相对于浅模块）是封装了大量功能在一个简单、可测试的接口中，且很少变化的模块。

与用户确认这些模块是否符合预期，以及哪些模块需要测试。

### 3. 编写并发布 PRD

使用以下模板编写 PRD。

---

## PRD 模板

### 问题陈述

从用户角度描述用户面临的问题。

### 解决方案

从用户角度描述问题的解决方案。

### 用户故事

一个长的、编号的用户故事列表。每个用户故事的格式为：

> 作为 <角色>，我希望 <功能>，以便 <收益>

示例：
> 1. 作为手机银行客户，我希望看到账户余额，以便更好地做出消费决策

用户故事列表应非常详尽，覆盖功能的所有方面。

### 实现决策

已做出的实现决策列表，可包括：
- 将构建/修改的模块
- 将修改的模块接口
- 开发者的技术澄清
- 架构决策
- Schema 变更
- API 契约
- 具体交互

不要包含具体的文件路径或代码片段。它们可能很快过时。

### 测试决策

测试决策列表，包括：
- 什么是好测试的描述（仅测试外部行为，不测试实现细节）
- 哪些模块将被测试
- 测试的先例（代码库中类似类型的测试）

### 范围外

此 PRD 范围外的事项描述。

### 补充说明

关于此功能的任何补充说明。
