# 代码库设计（深度模块）

> 共享的深度模块设计语言：大量行为通过小接口访问，放置在清晰的接缝处，通过该接口可测试。

---

## 核心理念

> "最好的模块是深的——大量功能通过简单接口访问。" — John Ousterhout《软件设计哲学》

### 深度模块 vs 浅模块

```
深度模块                    浅模块（避免）
┌──────────────┐            ┌──────────────────┐
│  小接口       │            │  大接口            │
│  (少量方法)    │            │  (很多方法/参数)    │
├──────────────┤            ├──────────────────┤
│              │            │                  │
│  深实现       │            │  薄实现            │
│  (复杂逻辑)    │            │  (简单委托)        │
│              │            │                  │
└──────────────┘            └──────────────────┘
```

---

## 设计原则

### 1. 小接口面积

- 越少的方法 → 越少的测试 → 越少的耦合
- 每个公开方法必须有存在的理由
- 问自己：这个方法是调用者真正需要的，还是我们觉得"可能有用"？

### 2. 深实现

- 将复杂度隐藏在接口后面
- 调用者不需要知道内部如何工作
- 实现可以彻底重构而不影响调用者

### 3. 清晰的接缝（Seam）

- 模块边界是天然的替换点
- 在接缝处设计接口，使模块可独立测试
- 接缝也是团队协作的边界

### 4. 通过接口测试

- 测试只通过公共接口
- 不测试私有方法或内部状态
- 重构内部实现时测试不应改变

## 设计检查清单

每次新增或修改模块时，逐项检查：

```
[ ] 接口方法数是否 ≤ 5？
[ ] 每个方法是否都有明确的调用场景？
[ ] 实现是否包含有意义的逻辑（而非简单委托）？
[ ] 模块是否可独立测试（通过接口，无需 mock 内部）？
[ ] 模块边界是否清晰（一个模块只做一件事）？
[ ] 依赖方向是否正确（高层不依赖低层细节）？
```

## 代码库架构扫描

定期（建议每 2-3 天）扫描代码库，识别架构退化：

### 扫描维度

| 维度 | 检查内容 | 警告信号 |
|------|---------|---------|
| 模块深度 | 接口/实现比 | 大量浅模块（接口方法 > 实现逻辑） |
| 依赖方向 | 模块间依赖 | 循环依赖、底层模块依赖高层 |
| 文件大小 | 单文件行数 | 单文件 > 500 行 |
| 接口面积 | 公开方法数 | 单模块公开方法 > 10 |
| 重复代码 | 相似代码块 | 3 处以上相似逻辑 |

### 扫描输出

生成 HTML 报告，列出：
1. 当前架构拓扑图
2. 深度模块评分（深/中/浅）
3. 需要优先深化的模块列表
4. 架构退化风险点

## 反模式

| 反模式 | 表现 | 修复 |
|--------|------|------|
| 传话筒模块 | 只转发调用，无自身逻辑 | 合并到调用方或内联 |
| 万能工具类 | 几十个不相关的方法 | 按职责拆分 |
| 过度抽象 | 只有一个实现的接口 | 删除接口，直接使用实现 |
| 泄漏的抽象 | 调用者需要了解内部细节 | 深化实现，隐藏细节 |
