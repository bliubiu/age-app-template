# DDD 领域驱动设计架构规范

> 通用 DDD（领域驱动设计）架构模式和开发规范。基于 [DDD 指南](https://ddd-fans.github.io/ddd-guideline/main.html) 最佳实践。在实现新功能、修复 Bug 或修改已有代码时必须遵循。

---

## 何时使用

- 新增聚合根、实体或领域服务
- 新增 Repository 端口和基础设施适配器
- 新增应用服务或命令处理器
- 新增领域事件或事件监听器
- 任何涉及领域/业务逻辑的代码变更

---

## 领域建模流程（Event Storming 十步法）

### Step 1：分析业务流程
列出所有业务场景，用业务语言描述。原则：用业务人员能听懂的语言，不要出现技术术语。

### Step 2：提取领域命令（Command）
从业务场景中提取用户/系统的意图（动词）。命令是意图，还没发生，用动词开头。一个业务动作 = 一个命令。

### Step 3：提取领域事件（Event）
从命令执行结果中提取已发生的事实（过去式）。事件是已发生的事实，事件是领域层发出的，不是技术事件。

### Step 4：建立 Command → Event 映射
一个命令可以触发多个事件。

### Step 5-6：完备性检查
- 每个事件是否都有对应的命令触发？
- 每个命令是否都产生了事件？

### Step 7：梳理 Event Chain（业务流程）
将事件串联成业务流程链。事件链 = 业务流程。一个事件可以触发下一个命令。

### Step 8：根据职责划分聚合（Aggregate）
同一生命周期在同一聚合。同一聚合内的对象一起创建、一起销毁、在同一事务内修改。不同聚合间通过领域事件通信。

### Step 9：找出跨聚合流程
跨聚合 = 通过领域事件通信，不能直接调用。

### Step 10：用 Saga / Process Manager 编排
对于复杂的跨聚合流程，使用 Saga 或 Process Manager 编排。

## 核心原则

### 0. 先判断是否需要聚合（最重要）

DDD 不是银弹。简单 CRUD 不需要聚合，直接操作数据库表即可。只有核心业务才需要聚合。

**判断流程：**
```
业务需求
  ├─ 是否有复杂业务规则？（状态机、校验、计算）
  │    ├─ 是 → 需要聚合
  │    └─ 否 ↓
  ├─ 是否涉及多个聚合协作？
  │    ├─ 是 → 需要聚合
  │    └─ 否 ↓
  ├─ 是否需要领域事件？
  │    ├─ 是 → 需要聚合
  │    └─ 否 ↓
  └─ 简单 CRUD → 直接操作数据库，不进领域层
```

### 聚合优先原则

能放聚合，不放领域服务。能放领域服务，不放应用服务。能放应用服务，不放 Controller。

### 1. 端口适配器架构（永远不要用四层架构）

基础设施层依赖领域层（依赖反转），领域层定义端口接口，基础设施层实现适配器。

```
domain         ← 领域层（聚合根、事件、命令、端口接口）
       ↑
infrastructure ← 基础设施层（Repository 实现、DAO、适配器）
       ↑
application    ← 应用层（服务、处理器、装配器、监听器）
       ↑
trigger        ← 接口层（REST Controller）
```

铁律：领域层绝不依赖基础设施层或应用层。

### 2. 聚合是充血模型，不是贫血模型

贫血模型是错误实践，永远不要用。聚合包含了自己的数据和逻辑。

### 3. 领域服务的定位

处理不属于任何单个聚合的领域规则。当某个业务规则需要多个聚合、多个实体共同参与，而找不到合适的归属聚合时使用。

### 4. Application Service 是薄编排层

负责加载聚合、调用聚合、持久化聚合、发布事件。不包含领域逻辑。

### 5. 聚合只存核心字段

读模型需要的字段由 CQRS 读模型负责，绝不能进聚合。

### 6-9. 判断标准

- **Command 的判断标准**：有业务意图、有业务规则、有业务结果
- **聚合的判断标准**：维护业务不变量
- **状态属于谁的判断标准**：状态属于行为方
- **聚合命名规范**：接口 `{Concept}`，实现 `{Concept}Aggregate`

## 聚合根模式（Interface + Impl 分离）

每个聚合根采用接口 + 实现分离，接口定义聚合的公开功能。

```
domain/model/aggregate/
  ├── AggregateRoot.java          ← 基接口
  ├── Order.java                  ← 接口（公开 API）
  └── impl/
      └── OrderAggregate.java     ← 实现（私有状态 + 逻辑）
```

---

## 领域事件模式

事件在聚合根状态转换时发射，通过 EventBus 发布，事务提交后语义（post-commit）。

---

## Command 模式

Command 是不可变值对象，表示外部对领域模块的期望。一个命令 = 一个事务。

---

## Repository 端口/适配器模式

整存整取：仓储要保证将聚合的信息完整保存，下次可以完整取出。

铁律：`save()` = INSERT，`update()` = UPDATE。已有聚合必须调用 `update()`。

---

## CQRS（命令查询职责分离）

当有复杂查询需求时，必须采用 CQRS。即使不存在复杂查询，采用 CQRS 也可以让领域模型更干净。

---

## 事务边界

事务边界在领域模块之外。一个命令 = 一个事务，原子性强一致。

---

## Saga（Process Manager）

聚合负责业务规则，Saga 负责流程编排。

---

## 反模式（永远不要做）

| 反模式 | 正确做法 |
|--------|---------|
| 贫血模型 | 聚合包含数据 + 行为 |
| 领域层依赖基础设施层 | 端口适配器，依赖反转 |
| ApplicationService 包含业务逻辑 | 业务逻辑在聚合或领域服务中 |
| 读模型字段进聚合 | 聚合只存核心字段 |
| save() vs update() 混用 | 已有聚合必须用 update() |
| 聚合直接持有其他聚合实例 | 聚合持有其他聚合的 ID 引用 |
