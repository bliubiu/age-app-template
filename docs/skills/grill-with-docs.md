# 文档审查（Grill with Docs）

> 对计划进行严格的文档审查，对照领域模型挑战计划，精炼术语，并在决策确定时即时更新文档。

---

## 审查流程

对计划的每个方面进行无情的访谈，直到达成共识。沿着设计树的每个分支走下去，逐一解决决策之间的依赖关系。对每个问题，提供你的推荐答案。

一次一个问题，等待每个问题的反馈后再继续。

---

## 领域感知

### 文件结构

大多数仓库有单一上下文：

```
/
├── CONTEXT.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `CONTEXT-MAP.md`，仓库有多个上下文：

```
/
├── CONTEXT-MAP.md
├── docs/
│   └── adr/                          ← 系统级决策
├── src/
│   ├── ordering/
│   │   ├── CONTEXT.md
│   │   └── docs/adr/                 ← 上下文特定决策
│   └── billing/
│       ├── CONTEXT.md
│       └── docs/adr/
```

## 审查期间

### 对照术语表挑战

当用户使用的术语与 CONTEXT.md 中的现有语言冲突时，立即指出。

### 精炼模糊语言

当用户使用模糊或过载的术语时，提出精确的规范术语。

### 讨论具体场景

当讨论领域关系时，用具体场景进行压力测试。发明探索边界情况的场景，迫使用户精确描述概念之间的边界。

### 与代码交叉引用

当用户陈述某事如何工作时，检查代码是否一致。如果发现矛盾，提出来。

### 即时更新 CONTEXT.md

当术语确定后，立即更新 CONTEXT.md。不要批量处理——在发生时捕获。

## CONTEXT.md 格式

```md
# {上下文名称}

{一两句话描述此上下文是什么以及为什么存在。}

## 语言

**订单**：
{简洁描述}
_避免使用_：购买、交易

**客户**：
{简洁描述}
_避免使用_：客户端、买家、账户

## 关系

- 一个**订单**产生一个或多个**发票**
- 一个**发票**属于一个**客户**

## 标记的歧义

- "account" 曾被用于表示**客户**和**用户**——已解决：这些是不同的概念。
```

### 规则

- **有主见**：当多个词表示同一概念时，选择最好的一个，列出其他作为避免使用的别名
- **明确标记冲突**：如果术语被模糊使用，在"标记的歧义"中明确指出
- **保持定义紧凑**：最多一句话。定义它是什么，不是它做什么
- **展示关系**：使用粗体术语名称，在有明显基数的地方表达
- **只包含此项目上下文特定的术语**：通用编程概念不属于
- **写示例对话**：展示术语如何自然交互

## ADR 格式

ADR 存放在 `docs/adr/`，使用顺序编号：`0001-slug.md`、`0002-slug.md`。

### 模板

```md
# {决策的简短标题}

{1-3 句话：上下文是什么，我们决定了什么，以及为什么。}
```

一个 ADR 可以只有一个段落。价值在于记录决策已被做出以及为什么——不在于填满各个部分。

### 何时创建 ADR

以下三个条件都满足时才创建：

1. **难以逆转** — 以后改变主意的成本是显著的
2. **没有上下文会令人惊讶** — 未来的读者会看着代码想"他们为什么这样做？"
3. **真正的权衡结果** — 有真正的替代方案，你为特定原因选择了一个

### 什么值得 ADR

- 架构形态（单体仓库、事件溯源）
- 上下文间的集成模式
- 带有锁定效应的技术选择
- 边界和范围决策
- 对明显路径的有意偏离
- 代码中不可见的约束
- 拒绝不明显的替代方案
