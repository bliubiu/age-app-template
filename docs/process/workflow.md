# 开发工作流程

## 工作模式

采用**任务驱动**的增量开发模式。每个任务都必须经过以下 10 个阶段，形成完整的开发闭环。

```
需求确认 → 任务拆分 → 实现 → 验证 → 审计文档 → 审计计划 → 闭包审计 → 文档化 → 提交 → 回顾
```

---

## 1. 需求确认

**目标**：确保双方对"做什么"和"怎么才算完成"有一致理解。

### 检查清单

- [ ] 包含原始需求、边界确认、需求理解、疑问澄清
- [ ] 有明确的需求描述和验收标准
- [ ] 有技术实现方案和技术约束
- [ ] 有任务边界限制和验收标准
- [ ] 有接口契约定义

### 产出物

- 任务文件（`docs/backlog/`）
- 需求文档

---

## 2. 任务拆分

**目标**：将需求分解为可独立交付的最小任务单元。

### 检查清单

- [ ] 已分析现有项目结构、技术栈、架构模式、依赖关系
- [ ] 按功能模块分解，确保任务原子性和独立性
- [ ] 每个任务有明确的验收标准
- [ ] 每个任务可以独立编译和单元测试
- [ ] 任务间依赖关系清晰

### 产出物

- 任务文件（`docs/backlog/`）
- 任务索引已更新

---

## 3. 实现

**目标**：基于任务文件编写测试和实现代码。

### 执行流程

```
红 → 绿 → 重构
  │    │    │
  ▼    ▼    ▼
写测试 → 写实现 → 优化
```

### 检查清单

- [ ] 先写测试（TDD），确保测试失败
- [ ] 编写最小实现使测试通过
- [ ] 重构代码保持测试通过
- [ ] 遵循编码规范和架构约束
- [ ] 遵循日志规范和错误处理规范

### 产出物

- 源代码
- 单元测试

---

## 4. 验证

**目标**：确认实现正确且符合预期。

### 检查清单

- [ ] 运行完整测试套件，全部通过
- [ ] 手动验证核心功能
- [ ] 检查代码与设计文档一致
- [ ] 检查性能是否达标
- [ ] 检查安全是否达标

### 产出物

- 测试报告
- 验证记录

---

## 5. 审计文档

**目标**：检查项目文档是否与代码实现一致。

### 审计内容

- **架构文档**：架构图、模块描述、接口定义是否与实现一致
- **API 文档**：API 描述是否与实际接口一致
- **README**：安装、运行、测试命令是否正确
- **CHANGELOG**：变更是否已记录

### 检查清单

- [ ] 架构文档与代码实现一致
- [ ] API 文档与实际接口一致
- [ ] README 命令可执行
- [ ] CHANGELOG 已更新
- [ ] 无过期文档

### 产出物

- 文档审计报告（`docs/audits/`）
- 文档修订（如需要）

---

## 6. 审计计划

**目标**：制定代码审查和质量检查计划。

### 审计内容

- **规范审查**：代码风格、命名、格式
- **需求审查**：实现是否覆盖所有需求点
- **安全审查**：加密、脱敏、权限控制
- **性能审查**：响应时间、资源使用
- **测试审查**：覆盖率、测试质量

### 检查清单

- [ ] 已确定审查范围
- [ ] 已确定审查标准
- [ ] 已确定审查人
- [ ] 已确定审查时间

### 产出物

- 审计计划文档（`docs/audits/`）

---

## 7. 闭包审计

**目标**：独立验证任务是否真正完成，防止过早宣布胜利。

### 审计维度

按 [驾驭工程五维模型](docs/standards/harness.md) 检查：

| 维度 | 审计问题 |
|------|---------|
| **Task Understanding** | Agent 是否理解目标和"完成"定义？ |
| **Controlled Execution** | 工作是否在可重复路径上？ |
| **Change Validation** | 是否有证据证明变更有效？ |
| **Reliable Delivery** | AI 速度是否绕过了质量检查？ |
| **Learning Capture** | 下一个任务是否受益于本次？ |

### 检查清单

- [ ] 测试覆盖了本次修改后的代码（非旧版本）
- [ ] 验收标准全部满足
- [ ] 代码审查已通过
- [ ] CI 检查已通过
- [ ] 无未解决的警告或错误
- [ ] 文档与实现一致
- [ ] 任务状态已更新为"已完成"

### 产出物

- 审查报告（`docs/audits/code-review.template.md`）
- 任务状态更新

### ⚠️ 重要

**闭包审计必须由独立的审查者（人类或另一个 Agent）执行**。实现者不能审计自己的代码。

---

## 8. 文档化

**目标**：更新项目文档，确保知识沉淀。

### 检查清单

- [ ] 项目进度文档已更新（`docs/backlog/index.md`）
- [ ] 项目知识库已更新
- [ ] 变更已记录在 CHANGELOG
- [ ] 相关 Skill 或规范已更新（如需要）
- [ ] 经验已沉淀（参见 `docs/standards/harness.md` 的 Loop Discovery）

### 产出物

- 更新后的文档
- CHANGELOG 更新

---

## 9. 提交

**目标**：将变更提交到版本控制。

### 检查清单

- [ ] 代码已格式化
- [ ] 无调试代码或临时代码
- [ ] 无敏感信息泄露
- [ ] 提交信息清晰描述变更
- [ ] 关联相关任务或 Issue
- [ ] 已推送到远程仓库
- [ ] 已创建 Pull Request（如需要）

### 提交信息格式

```
[类型] 简短描述

- 变更点 1
- 变更点 2

关联: TASK-XXX, ISSUE-XXX
```

类型：`feat | fix | docs | refactor | test | chore`

### 产出物

- Git 提交
- Pull Request

---

## 10. 回顾

**目标**：从本次任务中学习，改进下一次。

### 回顾问题

1. **是否重新猜测了启动命令？** → 写入 AGENTS.md
2. **是否在同一问题上再次犯错？** → 添加 Skill 或 Hook
3. **是否需要人工提醒某项检查？** → 固化为规范或脚本
4. **某个排查步骤是否连续有效？** → 强化该 Skill

### 经验沉淀决策树

```
发现可复用的经验
  ├─ 稳定事实 → 写回 AGENTS.md 或核心文档
  ├─ 重复方法 → 整理成 Skill
  ├─ 确定性操作 → 交给 CLI、脚本、Hook 或 CI
  ├─ 需要外部资源发现 → 使用 MCP
  └─ 高风险不可逆操作 → 保留权限边界和人工确认
```

### 检查清单

- [ ] 已回顾本次任务的摩擦点
- [ ] 已确定需要沉淀的经验
- [ ] 经验已按决策树归入对应位置
- [ ] 下一次类似任务能从本次受益

### 产出物

- 经验沉淀（Skill、规范、AGENTS.md 更新）

## 质量门禁

每个阶段完成时必须通过以下检查：

| 阶段 | 门禁 |
|------|------|
| 需求确认 | ✅ 验收标准明确 |
| 任务拆分 | ✅ 每个任务可独立测试 |
| 实现 | ✅ 测试全部通过 |
| 验证 | ✅ 手动验证通过 |
| 审计文档 | ✅ 文档与代码一致 |
| 审计计划 | ✅ 审查范围已确定 |
| 闭包审计 | ✅ 独立审查通过 |
| 文档化 | ✅ 文档已更新 |
| 提交 | ✅ CI 通过 |
| 回顾 | ✅ 经验已沉淀 |
