# 开发工作流

> 本文档定义项目的标准开发流程，融合 AGE 的 10 阶段工作流和任务驱动增量开发模式。

---

## 工作模式

采用**任务驱动**的增量开发模式，每个任务经过：

```
需求确认 → 任务拆分 → 实现 → 验证 → 文档化 → 提交
```

---

## AGE 10 阶段工作流

### Stage 0：读取上下文

AI 启动时必读文件：
- `AGENTS.md`
- `docs/context/project-context.md`
- `docs/context/conventions.md`
- `docs/architecture/system-baseline.md`

### Stage 1：收集原始输入

将 PM 笔记、原型截图、外部参考放入 `docs/input/`。

### Stage 2：澄清歧义（可选）

当需求模糊时，在 `docs/discussions/` 中记录澄清问题和结论。

### Stage 3：合成需求

将澄清后的需求整理为实现就绪的文档，放入 `docs/requirements/`。

### Stage 4：更新设计基线

- 业务/需求设计 → `docs/design/`
- 技术架构设计 → `docs/architecture/`
- 两者交叉引用，不混为一个文档

### Stage 5：审计文档

使用独立子 Agent 审查需求和设计文档，审查结果存入 `docs/audits/`。

### Stage 6：编写计划

触发条件：
- 变更 API、数据库/模型、认证、集成、部署
- 跨多个功能面变更
- 涉及多个模块
- 预计超过一个 AI Session

计划存入 `docs/plans/`。

### Stage 7：审计计划

使用独立子 Agent 审查计划，重点检查闭包门是否诚实、隐藏依赖、需求缺口。

### Stage 8：实现切片

- 一个真实功能切片 > 五个空壳页面
- 最小完整切片原则
- TDD 红-绿-重构循环

### Stage 9：验证

- 运行测试套件
- 手动/探索性测试记录存入 `docs/testing/`（可选）

### Stage 10：闭包审计

独立验证完成度：
- 实际行为匹配需求
- 证明存在于文件
- 文档已对齐

---

## 三步核心控制循环

```
A. 生成设计文档 → 需求设计 vs 架构设计分开写，互相引用，独立审查
        ↓
B. 生成 Plan → 从稳定基线出发，独立审查
        ↓
C. 定期审计 → 文档审计 + 计划审计 + 闭包审计
```

---

## 三级审计体系

| 审计类型     | 时机                    | 检查重点                                     |
| :----------- | :---------------------- | :------------------------------------------- |
| **文档审计** | 需求/设计更新后、实现前 | 范围边界、隐藏未解决问题、输入与需求一致性   |
| **计划审计** | Plan 写完后、实现前     | 闭包门是否诚实、隐藏依赖、需求缺口           |
| **闭包审计** | 实现完成后              | 实际行为匹配需求、证明存在于文件、文档已对齐 |

## 任务驱动开发流程

### 1. 需求确认

- 明确的需求描述和验收标准
- 技术实现方案和技术约束
- 任务边界限制
- 接口契约定义

### 2. 任务拆分

- 按功能模块分解，确保任务原子性和独立性
- 有明确的验收标准，尽量可以独立编译和单元测试
- 依赖关系清晰
- 创建 `docs/plans/` 下的任务文件
- 更新 `docs/backlog/index.md`

### 3. 实现

- 基于任务文件编写测试和实现代码
- 遵循 TDD 红-绿-重构循环
- 记录任务完成情况

### 4. 验证

- 验证执行结果
- 确认需求已实现
- 实现与设计文档一致

### 5. 文档化

- 更新 `docs/logs/` 记录变更
- 更新项目文档知识库
- 更新 `CHANGELOG.md`

### 6. 提交仓库

- 提交项目变更到仓库
