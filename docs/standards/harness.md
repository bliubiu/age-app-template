# 驾驭工程（Harness Engineering）

> 系统性地构建约束、工具、文档和反馈循环，使 AI Coding Agent 能够可靠地完成工作。
>
> 核心原则：**每次发现 Agent 犯错，就花时间设计一个方案，确保它不再犯同样的错误。**

---

## 核心理念

> **一个 Agent 友好的项目，不是安装了多少工具，而是：**
> - 项目知识能否被发现
> - 流程能否被执行
> - 结果能否被验证
> - 经验能否进入下一次任务

**"约束换自主"**：规矩越明确 → Agent 独立做的事越多 → 信任越高 → 自主权越大。

---

## 五步渐进式构建

不要试图在第一天就构建完美的 Agent 平台。按以下顺序，从一个真实任务开始，每次只沉淀一件最值得复用的经验。

### 第一步：AGENTS.md — 给 Agent 一张项目地图

假设新人第一天加入项目，你会告诉他什么？Agent 也需要同样的信息。

**值得写进去的，是 Agent 看不出来、却很容易猜错的事实：**

- 仓库里同时存在 npm 和 pnpm 的痕迹，当前究竟使用哪一个
- 某个目录看起来像源码，实际上由工具生成
- 完整测试需要半小时，修改一个模块时应该先运行哪条聚焦命令

**最小示例：**

```markdown
# AGENTS.md

- 安装依赖：`pnpm install`
- 修改后先运行：`pnpm test -- <相关测试>`
- 不要直接修改：`dist/`、`generated/`
- 修改模块边界前：阅读 `docs/ARCHITECTURE.md`
- 涉及数据库迁移或发布：先请求人工确认
```

**原则：渐进式披露** — 根目录只保留多数任务都需要的说明，更详细的架构、设计和工作流程，通过链接按需读取。

### 第二步：知识路由 — 把核心文档接到任务路径上

文档存在 ≠ 任务中能被找到。让文档从"仓库里有"变成"任务进行到这里时能被找到"。

**有效写法：给出读取条件，而非只放链接**

```markdown
- 修改模块边界前，阅读 `docs/architecture/system-baseline.md`
- 调整公共界面前，检查 `docs/design/app-overview.md`
- 改变发布流程前，阅读 Runbook
- 涉及加密或脱敏，查阅 `docs/standards/security.md`
```

**职责分离：**
- `AGENTS.md` 负责导航
- 核心文档负责解释
- 源码和测试提供最终事实

### 第三步：Skill — 从重复工作中提炼

有些任务不只是"知道什么"，还包含一套反复出现的判断和步骤。

**Skill 创建门槛（满足任一即可）：**

| 条件 | 说明 |
|------|------|
| 相似需求 ≥ 2 次 | 团队已经重复解释过 |
| 高成本 + 高风险 | 虽只发生一次，但很可能再次出现 |

**同时需确认：**
- 输入相对稳定、步骤能够复用、结果可以检查
- 没有被现有文档、脚本或其他 Skill 覆盖

**从哪里找第一个 Skill：**

翻看最近几次与 Agent 的对话：
- 哪些要求已经解释过两次？
- 哪些检查每次都要手工提醒？
- 哪些失败修复以后很可能再次出现？

### 第四步：CLI / MCP / Hook — 把流程变成可执行接口

Skill 定义了方法，要让流程真正运行，Agent 还需要可执行的工程接口。

**优先级：CLI 优先**

| 接口 | 适用场景 | 优先级 |
|------|---------|--------|
| **CLI** | 已有脚本或命令行工具 | 🥇 首选 |
| **Hook** | 确定性规则检查（禁止修改生成文件等） | 🥈 |
| **MCP** | 外部系统缺少 CLI 入口，需要结构化资源发现 | 🥉 |

**友好的 Agent CLI 应满足：**
- 能从 `--help` 中发现用法
- 支持非交互执行
- 输出稳定，必要时提供 JSON 等结构化格式
- 失败时返回明确的错误和退出状态
- 为耗时操作提供超时
- 修改外部状态前支持 `plan` 或 `dry-run`

**能力边界：**
- 能被程序明确判断的规则 → 交给脚本、Hook 或 CI 自动检查
- 涉及生产环境、凭据和不可逆操作 → 保留权限控制、沙箱或人工确认

### 第五步：Agent Work Loop — 让项目记住经验

Agent 完成修改后，别急着开始下一个需求。先确认：

1. 打开最终代码变更，确认测试覆盖的是这次修改后的版本
2. 检查是否走完了必要的 Review 和 CI
3. 代码写完只是过程的一部分，结果被验证和交付才算完成

**Loop Discovery — 每次任务结束后回顾：**

| 回顾问题 | 沉淀位置 |
|---------|---------|
| Agent 是否又重新寻找了一遍启动命令？ | → `AGENTS.md` |
| 是否在同一个目录上再次犯错？ | → Hook / CI 规则 |
| 是否仍然需要人提醒某项检查？ | → Skill |
| 某个排查步骤是否连续帮助了几次任务？ | → 强化该 Skill |

**经验沉淀决策树：**

```
发现可复用的经验
  ├─ 稳定事实 → 写回 AGENTS.md 或核心文档
  ├─ 重复方法 → 整理成 Skill
  ├─ 确定性操作/检查 → 交给 CLI、脚本、Hook 或 CI
  ├─ 需要外部资源发现或持续交互 → 使用 MCP
  └─ 高风险不可逆操作 → 保留权限边界和人工确认
```

> 写进仓库并不代表实践已经生效。等下一次类似任务到来，Agent 能否找到它、用上它，并因此少一次返工或提醒，才决定这项实践是否值得保留。

## Agent 常见失败模式

| 失败模式 | 表现 | AGE 应对 |
|---------|------|---------|
| **一步到位（One-shotting）** | 一个会话塞满所有功能，上下文耗尽 | 最小完整切片 + 闭包门 |
| **过早宣布胜利** | 看到部分完成就宣称任务结束 | 明确验收标准 + 独立验证 |
| **过早标记完成** | 写完成就标记，不做端到端测试 | 验证命令必须真实可执行 |
| **模式复制放大** | 代码库里有什么模式就忠实地复制并放大 | 架构约束 + Hook 拦截 |

## Agent Work Loop 五维模型

Better Harness 将 Agent 完成任务的过程抽象为五个维度，与 AGE 模板的资产映射如下：

| 维度 | 审查问题 | AGE 对应资产 |
|------|---------|-------------|
| **Task Understanding** | Agent 是否理解目标和"完成"定义？ | `AGENTS.md` + `docs/requirements/` |
| **Controlled Execution** | 工作是否在可重复路径上？ | `docs/skills/` + `docs/process/workflow.md` |
| **Change Validation** | 是否有证据证明变更有效？ | `docs/standards/testing.md` + 验证命令 |
| **Reliable Delivery** | AI 速度是否绕过了质量检查？ | 独立审查 + 闭包审计 + `docs/audits/` |
| **Learning Capture** | 下一个任务是否受益于本次？ | `docs/logs/` + `docs/bugs/` + CHANGELOG |

## 驾驭工程 vs AGE 模板

| 驾驭工程 | AGE 模板 |
|---------|---------|
| **上下文工程** — 结构化信息投喂 | `docs/context/` + `docs/architecture/` |
| **架构约束** — 机械化强制执行 | `docs/standards/` + CI 门禁 |
| **反馈回路** — 自动化测试沙箱 + 自修正 | TDD 红-绿-重构 + 独立审查 |
| **人类监督** — 审核员 + 环境设计师 | `ai-autonomy-policy.md` 自主性边界 |
| **渐进式披露** — 按需提供上下文 | `docs/index.md` 路由表 + 读取条件 |

## 快速自检清单

**项目当前阶段：**

- [ ] **能进入**：Agent 能否通过 `AGENTS.md` 正确启动项目？
- [ ] **能找到**：核心文档是否通过读取条件接到了任务路径上？
- [ ] **能复用**：是否有至少一个 Skill 沉淀了重复流程？
- [ ] **能执行**：关键操作是否有 CLI/脚本/Hook 支持？
- [ ] **能记住**：每次任务结束后是否回顾并沉淀了经验？

**持续改进不是不断增加配置，而是让这一次任务留下的东西，真正帮助下一次。**
